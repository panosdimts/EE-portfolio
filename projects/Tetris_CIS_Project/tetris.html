Java Tetris

A playable Java Swing Tetris implementation for CIS 1200. The game uses a 20 by 18 board, explicit game states, file-based save/load, JUnit tests, and Easy-mode undo.

Course CIS 1200
Status Completed
Platform Java desktop application
Tools Java 17, Swing, Maven, JUnit

Why It Belongs Here

This is a software project, not a hardware build. It is included because the state-machine, input, and testing problems are close to the way embedded firmware has to behave.

Verified Files

GameBoard.java TetrisGame.java InputHandler.java SaveManager.java TetrisTest.java

Objective

The project implements a desktop Tetris game in Java for CIS 1200. The finished application has menu states, scoring, pause behavior, save/load, high-score display, and undo in Easy mode.

Software Architecture

The implementation separates model, rendering, input, and persistence responsibilities. TetrisGame manages gameplay state and timers. GamePanel renders the Swing interface, InputHandler maps keys to state-aware actions, and SaveManager handles file I/O.

Model TetrisGame

Game state, timers, scoring, current and next pieces, undo snapshots.

View GamePanel

Swing rendering for board, active piece, next piece, score, menus, overlays.

Input InputHandler

Keyboard routing for menu, playing, paused, game-over, and high-score states.

Persistence SaveManager

Human-readable autosave file for state restore and top-score loading.

Board and Game Logic

  • GameBoard stores the board as a 20 by 18 two-dimensional integer grid.
  • Four invisible wall columns on each side use -1 values for boundary handling.
  • TetrisGame.canMove validates movement and rotation by checking bounds and occupied cells.
  • Placed tetrominoes are written into the grid by piece ID, which also drives rendering color.
  • Full rows are detected, cleared, and shifted downward by clearFullRows.

Input and State Management

The game uses explicit states: MENU, COUNTDOWN, PLAYING, PAUSED, GAME_OVER, and VIEWING_SCORES. Keyboard behavior changes based on the active state, which keeps menu navigation, gameplay controls, saving, loading, pausing, and restart behavior from collapsing into one input path.

  • Arrow keys move and rotate the active piece during gameplay.
  • Space drops the piece instantly.
  • P pauses or resumes depending on state.
  • S saves during gameplay or while paused.
  • L loads a saved game from the menu.
  • H opens high scores, and Escape returns from the high-score view.

Persistence and Undo

Persistence is implemented through SaveManager, which writes the game state, difficulty, score, top scores, board grid, and current/next tetromino data to autosave.txt. Undo is implemented in Easy mode using a Deque of snapshots containing the board grid, current piece, next piece, and score before placement.

Testing and Debugging

The repository includes JUnit tests for core logic in TetrisTest.java, including row clearing, score updates, tetromino rotation, and factory output validation. A course-provided compilation test remains in the cleaned source package.

Final Result

The final application is a playable Java Swing Tetris desktop game with menu states, countdown start, active and next-piece rendering, high-score display, scoring, pause behavior, save/load, and Easy-mode undo.

Formatted Project README

CIS 1200 Game Project Notes

A cleaned presentation of the project README with the implementation details most relevant to the finished application.

Core Concepts

File I/O

Save and load game state

SaveManager.java uses buffered file reading and writing to persist the board, pieces, scores, and difficulty. Saving and restoring structured game state made file I/O a central part of the implementation.

2D Arrays

Board representation

The board is stored as a two-dimensional grid. Cells encode empty spaces, wall markers, and piece IDs, which gives the game direct indexed access to collision, placement, and row-clearing behavior.

Collections

Snapshot-based undo

Undo uses a stack-like Deque of game snapshots. Each snapshot keeps previous board state, current piece, next piece, and score so Easy mode can restore a prior state consistently.

Inheritance

Piece hierarchy

Piece defines shared behavior for game pieces, while Tetromino extends it with concrete piece behavior such as rotation and duplication.

Class Overview

GamePanel.java
Renders the board, overlays, next-piece preview, menu text, score display, and other Swing UI elements.
InputHandler.java
Maps keyboard input to state-aware actions such as move, rotate, save, pause, load, and undo.
SaveManager.java
Handles file-based saving and loading through autosave.txt, including difficulty, score, board layout, and active pieces.
ScoreManager.java
Tracks current score, row-clear bonuses, placed-piece score, and top scores.
Piece.java and Tetromino.java
Model shared piece behavior and concrete tetromino rotation/copying.
Factory.java
Generates new tetrominoes randomly or by requested type.
Frame.java
Initializes the Swing window, game model, render panel, input handler, and repaint loop.
GameBoard.java
Maintains the grid, detects full rows, clears rows, and updates cells.
TetrisGame.java
Coordinates core gameplay: placement, state transitions, undo, timers, scoring, and top-score initialization.

Implementation Challenges

The hardest feature was undo. Restoring a previous move required more than replacing the board grid: the current piece, next piece, and score also had to return to a consistent state, especially after row clears.

File I/O was another debugging-heavy part of the project because the save format had to be read back in the exact order it was written. The README also notes that GamePanel took repeated refinement because the Swing rendering, overlays, and state-dependent text all needed to work together.

Design Reflection

The final design separates responsibilities across the game model, rendering panel, input handler, persistence layer, scoring, board representation, and piece hierarchy. If revisited, the README identifies GamePanel as a candidate for further modularization and suggests adding levels so the game increases speed and difficulty as score grows.

Lessons Learned

The project README describes undo and file I/O as the most difficult parts of the implementation. Restoring a previous board state while keeping the active piece, next piece, and score consistent required careful snapshot design, and loading structured save data required keeping the file format and read order synchronized.
